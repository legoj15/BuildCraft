# Platform layer (#98)

Standing design for moving every NeoForge use behind `buildcraft.platform` (Phase 1, NeoForge-only), then adding a `26.3-fabric` node (Phase 2). Synthesised 2026-11-03 from three competing proposals. The base is the "incremental-risk" design: in-tree packages, a compile-time binder and Stonecutter loader constants. Grafted onto it: the Fabric-shaped registration replay from "fabric-first", and the golden-save-first ordering, the no-generic-event-bus rule and the git-mv-ready package layout from "build-structure". Read this before writing or briefing any platform slice.

## Goal and finish line

- **Goal.** Common code (everything outside `buildcraft/platform/<loader>/**`) compiles against vanilla, BC and `buildcraft.platform` types only. Loader code lives in one package per loader. Phase 1 changes no behaviour on NeoForge, with one deliberate exception (the #117 fix, see Fluids), and adds no release target. A Phase 1 NeoForge behaviour that differs from `main` before the layer is a bug to restore, not a design choice: the review round of 2026-11 restored several (oil source spread, creative-tab order, BC events on the NeoForge bus, 1.21.1 `IItemHandlerModifiable` inventories, and the fluid-tank refusal rules recorded below).
- **Finish line, Phase 1.** Two things must hold, not one:
  1. The census (see Progress metric) reports zero live `net.neoforged` references outside `buildcraft/platform/neoforge/**` on the 26.3 view, apart from the explicit allowlist.
  2. Every patched-vanilla override (a NeoForge-injected method with no import, such as `getFlammability` or `writeClientSideData`) carries a `@LoaderHook` tag.
- **Which arms count.** The 1.21.1-only arms (`//?} else {` of `>=1.21.10`) do not count toward the finish line. That node is NeoForge-only forever, because Phase 3 excludes 1.21.x. Migrate them into the adapter whenever a slice already owns the seam (it removes directives for free), but never open a slice just for them.
- **The issue's criterion is replaced on purpose.** "No file outside `buildcraft.platform` imports `net.neoforged`" has three faults:
  - It is blind to patched overrides.
  - It can be gamed with fully qualified names (204 live before S1).
  - It counts types that may legitimately stay, such as `ModConfigSpec`.
- **Real gate into Phase 2.** `:26.3-fabric:compileJava` passes.

## Layout and build wiring

Verified facts this section rests on:
- Stonecutter 0.9.8 has user constants. The jar ships `build/config/ConstantContainer` (`put(String, boolean)`, `match(String value, String... candidates)`) and `ConstantDsl.constants(Action)`, and the Stitcher parser has a `ConstantExpressionContext` rule. So `//? if neoforge {` is valid directive grammar. Two scout reports said otherwise; they were wrong.
- Stonecutter registers processing for every Gradle source set, at `src/<sourceSetName>` (the string `src/\u0001` in `StonecutterBuildImplKt.createProcessingTasks`, iterated over `getSourceSets()` in `afterEvaluate`). A separate source set named `neoforge` would therefore be version-processed. An extra `srcDir` added to `main` would not. That kills the "extra srcDir of main" plan from the build-structure proposal.

**Phase 1 layout (in-tree; no new source set).**
- `src/main/java/buildcraft/platform/`: loader-neutral contracts, one interface per category (`platform.network`, `platform.menu`, `platform.event`, `platform.registry`, `platform.transfer`, `platform.fluid`, `platform.config`), the `Platform` binder, and BC-owned value types that only the seam needs.
  - **Contract rule:** these files may reference only the JDK, vanilla, other `buildcraft.platform` types, `buildcraft.api.fluids` (since S14d: `BCFluidStack` is vanilla-only and the Fabric node compiles that package, so the fluid storage contracts carry it) and `buildcraft.api.capability` (since S14e: the `BCCapability` token, which the API's MJ and pipe surfaces name, so it cannot live in the platform). Never a loader type, and never any other BC class. That is what lets a Fabric node compile the contracts alone.
  - **Nullness** in the contracts is marked with JSR-305's `javax.annotation.Nullable`, as the hook contracts do (the Fabric node has `jsr305` as a compile-only dependency, so it is available on every node). The rule lives in `platform/package-info.java`.
- `src/main/java/buildcraft/platform/client/`: client-only contracts plus the `ClientPlatform` binder. Reach them only from client init, so a dedicated server never loads them.
- `src/main/java/buildcraft/platform/neoforge/**` and `.../neoforge/client/**`: the NeoForge implementation. Each file keeps its `package` line live, and its whole body sits in `//? if neoforge {`. The precedent is `energy/compat/viewer/StirlingFuelSync.java`, which wraps its whole body in a `>=26.3` arm.
- `src/main/java/buildcraft/platform/fabric/**`: Phase 2, wrapped in `//? if fabric {`. On a NeoForge node it is an empty compilation unit.
- **Classes that are loader code by nature move whole into `platform/neoforge`.** Their logic is extracted to common code first. Examples: `RfEnabledCondition`, `AddOilBiomeModifier`, the `FluidType`/`BaseFlowingFluid` subclasses, `PipeBlockStateModel`, the `IClientBlockExtensions` implementations, and later the `@Mod` entrypoint. Do not wrap these in BC abstractions.
- **Tests:** NeoForge-specific tests (FML-JUnit pinning, `CapabilityHooks` behaviour, the override tags) go to `src/test/java/buildcraft/platform/neoforge/`. The rest stay where they are.

**Build wiring.**
- Root `gradle.properties` gets `loader=neoforge`. A Fabric node's `versions/<node>/gradle.properties` sets `loader=fabric`. The loader is never parsed out of the node name.
- `build.gradle.kts` reads `loader` and sets `stonecutter { constants.match(loader, "neoforge", "fabric") }`. Slice 1 must confirm with javap or a dry run that `match` sets exactly the matching key true and the others false; if not, use two `put` calls.
- **Node names:** the six NeoForge nodes stay unsuffixed. Fabric nodes are `<mc>-fabric`, declared as `version("26.3-fabric", "26.3")` (0.9.8 deprecates the short `vers()` at error level, so it does not compile). Renaming the existing nodes would churn every `:26.3:` task path, the skills, the hooks, the smoke runner and the release orchestrator, for nothing.
- **Phase 2 build shape (landed with the spike, #100):** everything NeoForge-specific (the `neoForge {}` block, its dependencies, mods.toml expansion, tests, game tests, the jar and `buildAndCollect`) lives in the buildSrc convention plugin `buildSrc/src/main/kotlin/bc.neoforge.gradle.kts`, its Loom twin is `bc.fabric.gradle.kts`, and `build.gradle.kts` keeps only the shared Stonecutter, toolchain and javac setup before `apply(plugin = "bc.$loader")`. ModDevGradle and Loom are `implementation` dependencies of `buildSrc/build.gradle.kts`, which is where their versions are pinned. Stonecutter flags reach the convention plugins as the `bcNode` extension (`buildcraft.gradle.BcNode`). Each convention plugin registers `nodeVerification`, the node's share of the root `fullTestSuite`. Never two plugin DSLs inline behind conditionals. Loom on 26.x does not remap, so shared source compiles as-is.
- **Phase 2 option, decided by the spike: not taken.** The option was to `git mv` `platform/neoforge` into a `neoforge` source set (`src/neoforge/java`, same package names, so no code edits), which would make "common never names an implementation" compiler-enforced. The cost is MDG `mods { sourceSet(neoforge) }`, test classpaths, the `buildcraft.test.mainSourceDirs` system property (`tasks.test` in `bc.neoforge.gradle.kts`), and a binder that is injected from the entrypoint, because main could no longer name the implementation. No `neoforge` source set exists (`bc.neoforge.gradle.kts` still builds `sourceSet(main)`); `platform/neoforge` and `platform/fabric` stay in `src/main/java` and the census enforces the rule.

**IDE.** The active node stays `26.3` (NeoForge). NeoForge implementation files are live; Fabric implementation files show as comments. To edit Fabric code, switch the active node to `26.3-fabric`.

**Rules for directives.**
- In common code, loader constants appear only on patched-override arms (see Patched-vanilla overrides), plus four documented exceptions: the REI annotations of the recipe-viewer plugins and the robot entity's class header (loader metadata); `api/events/BCEvent` and `ICancellableBCEvent` (BC's own events stay NeoForge `Event`s on NeoForge, see Events and lifecycle); and `BCFluidTank.movesNothing`, whose `neoforge && >=1.21.10` arm keeps NeoForge's refusal rule (see Transfer, review round). `platform/package-info.java` states the rule and lists only the first two, so it is a step behind.
- Everywhere else, loader differences live in loader packages, and directives in common code stay about MC version.
- Never use negation (`!fabric`); write the positive constant.
- Never nest a loader arm inside an MC arm in common code. Nesting MC arms inside a loader-gated implementation file is fine.

## Binding mechanism

**Compile-time binder.** `buildcraft.platform.Platform` has one static accessor per service, for example `Platform.loader()`. Each accessor reads a `static final` field in its own lazy holder class, so touching `loader()` never loads the network implementation.
- The only loader directive in the binder is inside each holder: the `neoforge` arm constructs the NeoForge implementation, and the `fabric` arm is commented on NeoForge nodes.
- `ClientPlatform` is the client-only twin.

**Rejected alternatives.**
- **ServiceLoader** (fabric-first): it needs a `META-INF/services` file per interface. It adds a failure mode inside FML's module layer and under FML-JUnit class-init ordering (`robotics/entity/UnreachableEntityCache.java` documents exactly such a static-init chain). It buys nothing when each jar ships one loader.
- **Same-name class per loader with no interface** (build-structure): nothing checks the Fabric copy against the NeoForge contract until the Fabric node compiles.

**Cost.** One `getstatic` of a constant static final, plus a monomorphic `invokeinterface`. The JIT inlines both, so the steady-state cost is zero. The real cost is adapter allocation at transfer boundaries:
- Implementations must cache foreign-handler adapters (`BlockCapabilityCache` on NeoForge, `BlockApiCache` on Fabric, or identity-keyed).
- They must never wrap a handler on every tick.
- **As built (accepted trade-offs).** The rule above is met only partly, on purpose; nothing here changes behaviour.
  - `lib.transfer.AdapterCache` gives one adapter per wrapped storage or handler, keyed and valued weakly, so a capability query answers the same object twice only while something holds the adapter. A per-tick caller that drops its view after each use (the pump's `FluidUtilBC`, `TileHeatExchange`, the `PipeFlowFluids` face lookup, `DockingStationPipe`, the FE engine) reuses it only until a GC clears the weak value: the saving is real but GC-dependent. Holding the view, or a `BCLookupCache`, in those callers is the follow-up if profiling ever shows the garbage.
  - `TransferServices.itemCache`/`fluidCache` and `BCLookupCache` have no caller; `TransferAccess.findItem`/`findFluid`/`findEnergy` allocate a fresh adapter per call, as do the capability providers (a stateless wrapper per query) and the item scans (a stack copy per slot visited). All perf-only, all deferred.
  - On 1.21.1, `LegacyTransactions` drops a committed nested snapshot when the parent already holds an older one (the older wins) instead of parking it for reuse. The dropped snapshot is an allocation on a nested commit and nothing more; the per-tick push its class Javadoc describes is not affected. Deferred as perf-only.
  - `DeferredFluidCalls` is held by its owning view, so a transaction that queued a call keeps that view, and the calls it owes, alive until it closes.

**Implementation rule.** Implementations read loader state per call and never cache loader statics in their own static initialisers.

**Registration timing (graft from fabric-first).** Seams are shaped like Fabric: plain register calls made during BC init, with no mod bus in sight.
- NeoForge implementations queue those calls and replay them inside the matching event (`RegisterCapabilitiesEvent`, `RegisterMenuScreensEvent`, `EntityRenderersEvent.RegisterRenderers` and so on).
- On Fabric the same calls run immediately. That keeps the Fabric side to one-liners and keeps the NeoForge replay ordering identical to today's registration order.

## Seam per category

Seam shapes, in order of preference:
1. Move the body of an existing BC helper into the implementation and leave its call sites alone.
2. Use a register-call sink (replayed on NeoForge).
3. Use typed hooks with vanilla-typed functional interfaces.
4. Use a BC-owned value type, only where no shared shape exists.

Never build a generic BC event bus. It is the Architectury trap the issue rejects.

**`api/` rule.** `buildcraft/api/**` never imports `buildcraft.platform`. BC-owned types that the API exposes live in `buildcraft.api.*`. No addon exists, so API signatures may change in Phase 1.

### Loader services
- **Shape.** `LoaderServices`: `isPhysicalClient()`, `isModLoaded(id)`, `modIds()`, `modVersion(id)` (an `Optional`), `modSourcePaths(id)` (`List<Path>`), `configDir()`, `gameDir()`, and `currentServer()` (nullable).
- **Typing.** BC-owned. Fabric maps to `FabricLoader` and `getOrigin().getPaths()`, and captures `currentServer` at `SERVER_STARTING` and clears it at `SERVER_STOPPED`.
- **Format risk.** None.
- **Directive interplay.** Done in S16: the 1.21.1 `getDist()` to `.dist` regex is gone from `build.gradle.kts`; `NeoForgeLoaderServices.isPhysicalClient` carries the `>=1.21.10` arm, and `api/core/NbtApiUtil.java` asks the source lib installs (`setRegistryOpsSource`) instead of FML.

### Config
- **Shape.** `ConfigRegistrar.register(BCConfigType, spec, fileName)`, where `BCConfigType` is a BC enum (COMMON, CLIENT, LOCAL), plus `ConfigHooks.onReload`.
- **Typing.** The 26.3 `LOCAL` versus `COMMON` directive (`core/BCCore.java:116-124`) moves into the implementation. `ModConfigSpec` itself stays NeoForge-typed in the 9 config classes and is allowlisted, pending the user's choice of Forge Config API Port or an in-house builder.
- **Format risk.** The toml file names and keys must not change. Diff the generated tomls before and after.
- **Unverified:** whether Forge Config API Port supports `LOCAL` on 26.3. That gates the open question below.

### Events and lifecycle
- **Shape.**
  - `GameHooks` has one typed method per event kind used today (about 35). Each takes a vanilla-typed functional interface; cancellable hooks return a boolean meaning "cancel".
  - `HookOrder` (EARLY, DEFAULT, LATE) appears only where BC depends on order today: `ContainedFluidDetonation` and `LocalBlockUpdateNotifier` at LOWEST, silicon `LoggingIn` at HIGH, and the `receiveCancelled` pair in `MachineRefusals`.
  - `LifecycleHooks` covers common setup with an `enqueueWork` equivalent, load complete, server about-to-start and stopped, and level save.
- **`PlatformProtection`.** `canBreak`, `canPlace`, `canAttack`, and the right-click and use-item simulations. It absorbs `BreakEventCompat`, `PlaceEventProbe`, the `AttackEntityEvent` posts (`RobotProtection`, `StripesHandlerMinecartDestroy`), `CommonHooks.onRightClickBlock`/`onItemRightClick` (`BlockUtil.java:404,448`) and `EventHooks.doPlayerHarvestCheck`/`onBlockPlace`. `useItemOn` is a machine's click with the placement capture a player's gets (NeoForge's patched `ItemStack.useOn`). On Fabric the checks go to Fabric API's player callbacks and to Common Protection API (`eu.pb4:common-protection-api`, MIT, bundled jar-in-jar), the API Fabric claim mods answer through, about the fake player's owner; a refusal from either refuses (a callback answering anything but `PASS` stops the act). Two checks have no provider question: `canHarvest` is vanilla's tool check (Fabric has no harvest-check event; its only caller uses it for dig speed, not as a veto), and an item used in the air asks the providers whether the block the player stands in may be interacted with, since the API has no item-use check. Fabric has no place event: `canPlace`/`canPlaceOver` ask the providers alone, as NeoForge's placement event is all a machine's placement asks there (vanilla's `mayInteract`, spawn protection and the world border, gates a player's click packet, never a machine); `useItemOn` records the blocks the use sets (`LevelMixin`) and puts them back when a provider refuses one, in reverse, with drops and experience suppressed while it runs (`BlockDropsMixin`, NeoForge's `restoringBlockSnapshots`); and `GameHooks.onBlockPlace` listeners see these machine placements only. Fabric gaps: a claim mod guarding placements through its own mixins alone is not asked; the refused placement's own side effects and neighbour updates have already run when it is put back (NeoForge defers them); the `onBreak` listeners share one `PlayerBlockBreakEvents.BEFORE` callback, because Fabric events cannot be unregistered (a closed registration leaves nothing behind). The Fabric claim-mod tests stand a provider up through `LoaderTestEvents.claimPlacements`; the break, interact and damage asks of the providers have no test yet (#130).
- **Fabric: mixin-fed hooks.** Where Fabric API has no event, a mixin in `platform.fabric.mixin` calls a `FabricGameHooks.fire...` method where NeoForge posts its event, with the same arguments: the chunk sent to a player (`PlayerChunkSender.sendChunk`, after the packet), the spawn finalize (`Mob.finalizeSpawn`'s head), the death drops (`LivingEntity.dropAllDeathLoot` collects what `spawnAtLocation`, `LivingEntity.drop`, `EntityEquipment.dropAll` and `Inventory.dropAll` drop, NeoForge's `captureDrops` sites, shows the list to the listeners, then puts it in the level), the neighbour notify (`ServerLevel.updateNeighborsAt`/`updateNeighborsAtExceptFromFacing` and `DiodeBlock.updateNeighborsInFront`), the explosion (`ServerExplosion.hurtEntities`, once the entity list is gathered: both lists are the ones the blast goes on to use), each player's own tick (`Player.tick`'s end), a fake player's entity interaction (`Player.interactOn`'s head, after the spectator branch, as NeoForge: Fabric API asks only a real player's click, in its packet handler; `fireFakePlayerEntityInteract` asks Common Protection API's `canInteractEntity`, then `UseEntityCallback`, and a refusal is what `interactOn` answers) and the client level's unload (`Minecraft.setLevel`, `disconnect`, `clearClientLevel`, client mixin). The game tests post the same `fire...` methods through `LoaderTestEvents`, and see game events through the game-test mod's `ServerLevelGameEventMixin` (NeoForge's `VanillaGameEvent` point). `HookOrder` EARLY/LATE are BuildCraft phases ordered before and after Fabric's default phase (`FabricGameHooks.register`, which the game tests' claims use too). A `receiveCancelled` `onEntityInteract` listener is told how a fake player's click ended: one before the refusing callback saw it allowed, the others are told it was refused, and a LATE one is told only once the callback has ended, so it sees every listener's answer whatever their registration order. Gaps: `syncRecipeTypes` (Fabric syncs recipes per serializer; kept a gap on purpose: on 26.3 a `RecipeSerializer` is a record of codecs with no recipe type, both sides must declare serializers at mod init, so mapping a `RecipeType` to its serializers takes a static table of vanilla's and BuildCraft's ids that silently misses other mods' serializers, a design decision for the owner); a refused real-player entity click never reaches a `receiveCancelled` listener after the refusing callback (Fabric API ends the event in its packet handler; nothing in BuildCraft asks about real players); `onBlockPlace` sees machine placements only (a player's placement still reaches the neighbour-notify listeners); the spawn finalize is seen only through `Mob`'s own `finalizeSpawn` (an override that never calls it, or a spawner that skips the finalize, posts nothing).
- **Typing.** BC-owned hooks over vanilla types; listeners are wired in per-subsystem classes in the implementation.
- **`@EventBusSubscriber` classes.** The six of them become explicit hook registrations. `FakePlayerUtilSubscriptionTester` and `LevelUnloadSubscriptionTest` reflect over `@SubscribeEvent`, so they are rewritten to test registration or behaviour.
- **Entrypoint (late slice).** `@Mod` moves to `platform/neoforge/BCNeoForgeEntrypoint`, which captures the mod bus. The 51 `init(IEventBus)` signatures become `init()`.
  - **As built (S10).** The entrypoint sets `NeoForgeModBus` (the bus and container every NeoForge implementation used to find through `ModLoadingContext.getActiveContainer()`), subscribes the one `RegisterCapabilitiesEvent` listener, then runs `BCCore.init()` and, on a physical client, `BCCoreClient.init()`. The client init used to run in the middle of `BCCore`'s constructor; nothing after that point listens to an event it listens to, so no event's listener order changed. Capability registration is a NeoForge-typed stopgap until the transfer slice: `lib.misc.CapabilityListeners` collects the subsystems' listeners in init order and the entrypoint's listener runs them. The model events left in common code became `ClientRegistrationSinks.onModelsBaking`, `editBakedModels` (vanilla `ModelBakery.BakingResult`, the model map on 1.21.1) and `onModelsBaked(HookOrder, ...)`, each added straight to the bus at its call so every listener keeps its place. Fabric: `BCFabricEntrypoint` and `BCFabricClientEntrypoint` run the same inits (compiled since Phase 2a); `editBakedModels` cannot run there (Fabric has per-model after-bake modifiers only).
- **As built (Fabric lifecycle, review round).**
  - `LifecycleHooks.onLateBlock(Consumer<Block>)`: Fabric uses Fabric API's registry-entry-added event for the block registry, NeoForge a no-op, because FML runs the setup actions after every register event. Fabric still runs the setup actions inside BuildCraft's own initializer, so `onLateBlock` is how its two registry scans take in blocks that later-initialised mods register: the soft-block scan (`BCCore.addIfSoft`) and the wrench-rotation class scans (`CustomRotationHelper.registerClassHandlersFor`). The `setup_scans_find_late_registered_blocks` game test pins it with test-only blocks.
  - `ConfigHooks.onLoad`: Forge Config API Port reads a COMMON or CLIENT spec inside its `register()`, so the loading event has fired before any hook can subscribe and is not replayed. `FabricConfigHooks.onLoad` therefore runs its action at once for a spec that is already loaded (a non-default `miningMultiplier` applies from game start). NeoForge loads after construction and is unchanged.
  - `LevelLifecycleBlockEntity.onJoinedLevel`: on Fabric the queue drains at the head of each server level's `tickBlockEntities` (`LevelMixin`), after that tick's scheduled block ticks, as NeoForge's `onLoad` does.
  - `BCMenus`: an extended menu type may be opened only through `BCMenus.open`, and `open` takes only types made by `BCMenus.create` (Fabric throws on a mismatch).
  - `FabricRegistryServices`: a registrar subscribed after `registerPending` (another mod's initializer, the game-test mod) now also builds the entries it registers after `subscribe()`; `registerPending` loops until the queue is empty, since a factory may register more entries; a factory that threw is remembered and reported as the cause of the later failure instead of a construction cycle.
  - Fabric config screen: `ClientConfigScreens` is a seam of its own (`ClientPlatform.configScreens()`, called as `registerConfigScreen()` from `BCCoreClient`), not part of `ClientRegistrationSinks`. NeoForge's implementation registers its `ConfigurationScreen` extension point; `FabricClientConfigScreens` offers Forge Config API Port's `ConfigurationScreen` through its `ConfigScreenFactoryRegistry`, which Mod Menu reads (no screen without Mod Menu installed). Built and compiled, not yet opened in a client: confirm in-game.
- **Format risk.** None. Order risk: record the observed order before changing any priority. **Checked (review round):** at the first port, transport's creative-tab listener was `EventPriority.LOW` and silicon's `LOWEST`, so transport's plugs and wires came before silicon's gates and plugs, while the comment in `BCTransport` said the opposite. The comment is rewritten; the order is unchanged, and now follows from `BCCore` calling `BCTransport.init()` before `BCSilicon.init()` (`CreativeTabContents` keeps contributions in call order).
- **Directive interplay.** The render-stage and other event-class cliffs move into the implementation with their directives.
- **BC's own events (S16).** `api/events/*` and `EventBuildCraftReload` each hold a `LISTENERS` constant, a `buildcraft.api.events.BCEventListeners` (one typed list per event, run in registration order; a cancelled `ICancellableBCEvent` skips the later listeners). It is a list, not a bus: no dispatch by type, no priorities.
  - **Posted on the NeoForge bus on NeoForge (review round, open question 3 taken).** `BCEvent` extends NeoForge's `Event` there (behind `neoforge` arms in `BCEvent` and `ICancellableBCEvent`), and `BCEventListeners.post` runs the BuildCraft list first, then posts the event on `NeoForge.EVENT_BUS` with the cancel state the list left, so an addon's `@SubscribeEvent` or `addListener` on BuildCraft's reload and robot events (place, interact, dismantle) still receives every post and can cancel robot placement and dismantling, as before the layer. Fabric has no loader bus: the list is all there is.
  - This is a deliberate exception to "`buildcraft/api` names no loader" (addon source compatibility). The census allowlist entry `api-events-on-neoforge-bus` is therefore permanent, and the allowlist will not end empty.
  - The client level-unload hook no longer clears marker caches: `MarkerCache` drops its client tables per level through `GameHooks.onLevelUnload` on both loaders. `ClientHooks.onClientLevelUnload` is still used by `BCRoboticsClient` and `BCTransportClient`. The client-wide marker sweep that #115 added for Fabric (`MarkerCache.onClientWorldClosed`) was removed again: NeoForge never had it, and every level's own tables are already dropped on its unload on both loaders, so leaving a world still clears markers and connections.

### Networking
- **Shape.** `BCNetwork`:
  - Registration: `clientbound`, `serverbound` and `bidirectional`, each taking `(Type, StreamCodec, PacketHandler)` with an optional version string.
  - Sending: `sendToServer`, `sendToPlayer`, `sendToTrackingChunk(ServerLevel, ChunkPos, p)` and `sendToDimension`.
  - `registryBuf(ByteBuf, RegistryAccess)` absorbs `ConnectionType.NEOFORGE`.
  - The BC-owned `PacketContext` offers `player()`, `runOnMain(Runnable)` and `reply(payload)`. `runOnMain` is NeoForge `enqueueWork`; on Fabric it is the server context's `server.execute` for a serverbound payload and the client context's `client().execute` (`FabricClientNetwork`) for a clientbound one, so a clientbound handler runs on the render thread.
- **Typing.** Payload records, codecs and `CustomPacketPayload` are vanilla and stay common.
- **Format risk.** None, provided the ids, codecs and `versioned("2")` on MessageMarker (`BCCore.java:323`) are preserved exactly. Three handlers skip `enqueueWork` today (`MessageMarker`, `MessageDebugRequest`, `MessageDebugResponse`), and the seam must keep that difference.
- **Directive interplay.** The `ClientPacketDistributor` directive (5 sites) and the 3-arg versus 4-arg `playBidirectional` directive (`BCCore.java:339-352`) collapse into the implementation.
- **Fabric gaps (`FabricNetwork`).** Fabric has no per-payload version negotiation, so the `version` argument is unused and a mismatched peer misreads instead of being refused at login. The payloads are registered without Fabric's `registerLarge` splitting, and vanilla's frame decoder caps a packet at a 21-bit length, so one above that size (a huge blueprint in a `SnapshotResponsePayload`) fails to send where NeoForge's `GenericPacketSplitter` would split it. Neither was on the accepted-gaps list of the original brief; both are deferred (follow-up).

### Menus
- **Shape.** `BCMenus.create(BufferMenuFactory<T>)` takes `(id, Inventory, RegistryFriendlyByteBuf)` and covers the 26 `IMenuTypeExtension.create` calls. `BCMenus.open(ServerPlayer, MenuProvider, Consumer<RegistryFriendlyByteBuf>)` covers the 14 `openMenu` calls.
- **Keep the raw writer, not typed opening data.** That keeps the bytes identical. On Fabric the writer fills a `byte[]` sent through `ExtendedMenuProvider` with `ByteBufCodecs.BYTE_ARRAY`.
- **Typing.** `IBCMenuProvider` becomes BC-owned. The `writeClientSideData` override stays as a tagged hook, because the spectator path (`ServerPlayerGameMode`, `openMenu(provider)` with no writer) relies on it. The five anonymous two-argument providers (list, gate, diamond, Emzuli and wood-diamond pipes) move onto `IBCMenuProvider` in the same slice.
- **Format risk.** Low.

### Registries and data
- **Shape.**
  - `BCRegistrar<T>`: `create(ResourceKey<Registry<T>>, modid)`, `register(name, Supplier)`, and block and item helpers that absorb `RegistrationUtilBC` (its eager versus supplier cliff) plus the 42 direct `registerSimple*` bypasses.
  - One helper for the `>=26.3` feature-registry split, which is copied three times today.
  - `BCHolder<T>` implements `Supplier<T>` and offers `id()`, `key()` and `holder()`. `BCBlockHolder` and `BCItemHolder` also implement `ItemLike`.
- **Typing.** On NeoForge, `BCHolder` wraps `DeferredHolder`. The 205 holder uses are a scripted type swap.

### Fluids (value type)
- **Shape.** `buildcraft.api.fluids.BCFluidStack` mirrors NeoForge `FluidStack`'s method names (`EMPTY`, `getFluid`, `getAmount`, `grow`/`shrink`, `copy`, `copyWithAmount`, `isSameFluid`, `isSameFluidSameComponents`, `getComponents`, `CODEC`, `OPTIONAL_CODEC`, `STREAM_CODEC`, `getHoverName`). They stay as the rest of the `FluidStack` mirror, for addon code written against NeoForge's type; the class Javadoc says so. `StackKey` hashes a fluid without its amount, as its `equals` compares it.
- **Typing.** BC-owned. Conversion happens only in `platform/neoforge`.
  - Built (S13a): `NeoForgeFluids.toNeo`/`fromNeo` and Fabric's `FabricFluids` (`FluidVariant`, x81 droplets, floored back). `getHoverName` goes through a provider that `BCLib` installs from `Platform.fluids()` (`FluidServices`), since the api may not name the platform. The Fabric node also compiles `buildcraft/api/fluids/**` to keep the type loader-neutral.
  - Swapped (S13b): every BC signature, field and local now holds `BCFluidStack` (api, lib, factory, energy, transport, builders, robotics, core, client and compat code, and the tests). NeoForge `FluidStack` stays only where a NeoForge signature demands it: the 1.21.1 `IFluidHandler` implementations, `BCFluidTank`'s inherited `onContentsChanged`, `FluidType.canFillFluidType` in `BCCore`, and `FluidUtil` calls. Those sites and every `FluidResource`/`toStack` boundary convert through `lib.fluid.NeoFluidStacks`, the common twin of `NeoForgeFluids` (common code may not name `platform.neoforge`). S14 moves them into `platform/neoforge` and deletes it.
  - Done (S14d): `NeoFluidStacks` is gone. Fluid storages are `BCFluidStorage` (`platform.transfer`, `int` mB, `BCFluidStack` resources) on every node; `BCFluidTank` implements it itself (the `FluidStacksResourceHandler` semantics, journalled per slot) and keeps both save formats. `NeoForgeFluidStorages` adapts both ways (`ResourceHandler<FluidResource>` / 1.21.1 `IFluidHandler`), `FabricFluidStorages` over `Storage<FluidVariant>`. Left NeoForge-typed: the fragile fluid container's `SimpleFluidContent` component and its item capability (BCCore), the `FluidType` subclasses in `BCEnergyFluids`, and the robot API's fluid surface (`IFluidHandlerAdv`, `DockingStation` getters), which crosses through `TransferServices.to/fromLoaderFluidHandler` until S14f.
- **Format risk is high.** `CODEC` must emit NeoForge's exact shape (`id`, `amount`, `components`). It is used in the `SimpleFluidContent` component (`BCCore.java:63-65`), `RequiredExtractorTank` snapshots, and the distiller, heat-exchanger and robot NBT. A codec-parity test is written first.
- **Properties.** `FluidType` reads (density, viscosity, temperature, lighter-than-air, bucket, sounds) go through a BC `FluidProperties` record. The NeoForge implementation builds the `FluidType` from it, and `BCEnergyFluids`' subclasses move whole.
  - Built (fluid-properties slice): BC fluids register through `platform.registry.BCFluidRegistrar` (`BCFluidRegistrar.create(ns)`, from `Platform.fluids().createRegistrar`). It takes a `FluidProperties` record (the type properties plus the flow parameters; `motionScale` is a `DoubleSupplier`, so the sticky-oil config is read on every use) and a `platform.FluidBehaviour`. The behaviour is the common half of the old subclasses: their tick, spread and replace rules (gas detonation, dense oils sinking, spreading over water, sources refusing water) live in `BCEnergyFluids.OilBehaviour` and reach vanilla's protected flow steps through `platform.FluidFlow`, which every registered fluid implements. `NeoForgeFlowingFluids` (moved from `BCEnergyFluids`) builds the `FluidType` and the `BaseFlowingFluid` pair and calls the hooks. Ids and registration order are unchanged: the type under the fluid's name, then the source, then `_flowing`.
  - The source and flowing forms differ on purpose in `OilBehaviour`: only the flowing form returns early (no spread) when the fluid below is its own, while the source form always forces the spread (a light oil or fuel source resting on a block of its own fluid spreads into every open side again, as before the layer; the layer had narrowed it to the side next to a drop). The form is read off the fluid instance, not the block state. Fabric shares `OilBehaviour`, so the source-form rule applies on `26.3-fabric` too, with no `main` baseline to compare there.
  - Fabric: `FabricFlowingFluids` is a vanilla `FlowingFluid` pair matching `BaseFlowingFluid`, plus a `FluidVariantAttributeHandler` (temperature, viscosity, gas flag, bucket sounds). Fabric has no fluid type, and every BC fluid is in `minecraft:water` (the spread rules need it), so vanilla's entity physics treated them all as water. `FabricFluidPhysics` and its mixins (`EntityFluidInteractionMixin`, `EntityMixin`, `LivingEntityMixin`, `FloatGoalMixin`, `ItemEntityMixin`, `AbstractBoatMixin`) answer at NeoForge's patch points from the declared properties: in water and eyes in water (`baseTick`, `updateFluidInteraction`) mean a water-like fluid, drowning (`baseTick`'s breathe test) follows `canDrown`, each fluid pushes with its own current and `motionScale` where `canPushEntity`, a fluid that is not water-like halves the fall distance each tick (NeoForge's default modifier), and the fluid's `entityInside` extinguishes where `canExtinguish`. A mob's `FloatGoal` floats only where `canSwim` (`FloatGoalMixin`); a non-BuildCraft fluid is judged by the goal's own `entity_floatable` tag, as in vanilla. A dropped item in any BuildCraft fluid deeper than 0.1 takes the water item movement (`ItemEntityMixin`, NeoForge's `setItemMovement`), so items bob in crude oil and residue instead of sinking to the floor. A boat floats on no BuildCraft fluid (`AbstractBoatMixin`, NeoForge's `canBoatInFluid`: five vanilla water-tag tests, four `FluidState.is` wraps plus `canAddPassenger`'s eye test), so it sinks in oil and fuel; a boat on water is unchanged. A living entity in a fluid that is not water-like (crude oil, residue) wades through it by the common `platform.ThickFluidMotion` on both loaders: NeoForge's `travelInFluid` has moved a non-vanilla type that implements no `FluidType.move` neither as water nor as lava since 26.1.2 (issue #117: it held an entity in crude oil in place), so the NeoForge type overrides `move` on >=26.1.2 (1.21.x keep NeoForge's own water/lava fallback), and `LivingEntityMixin` takes the same step plus NeoForge's `jumpInFluid` lift. Pinned by the seven `FluidPhysicsTest` game tests on both loaders (`crude_oil_floats_items`, `crude_oil_does_not_float_boats` and `crude_oil_current_pushes_items` are the review round's; the last is the first test of a BuildCraft fluid current's push on Fabric). Remaining physics gap, behaviour undecided (see `ThickFluidMotion`'s Javadoc): a ridden horse (`can_float_while_ridden`) in crude oil rises on NeoForge 26.3 only, through vanilla's unconditional `floatInLiquidWhileRidden`, and sinks on NeoForge 26.1.2 and 26.2 and on Fabric. Mirroring the lift on Fabric would enshrine a vanilla side effect the #117 design (sink gently) never intended.
  - The #117 override is on `>=26.1.2`, which the directive cannot narrow by patch. The 26.1 node's jar also runs on NeoForge 26.1.0 and 26.1.1; the override is inert on the 26.1.0 beta (its `FluidType` has only the older `move(FluidState, LivingEntity, Vec3, double)` signature), and 26.1.1 is unverified. A runtime version gate is a design choice left open.
  - Reads of any fluid are `FluidServices` accessors (`viscosity`, `isLighterThanAir`, `isSameKind`, `description`) rather than a `FluidProperties` per call, since another mod's fluid has only those to give. Fabric answers BC fluids from their declared properties.
- **Units.** Integer mB internally. The Fabric adapter multiplies by 81, floors offers, and extracts in whole mB, so a foreign move is whole millibuckets or nothing (see Transfer, Fabric transfer for the cauldron case). That is an accepted Fabric-only gap (open question 4, taken).
- **Client.** `IClientFluidTypeExtensions` and `RegisterFluidModelsEvent` sit behind a client fluid sink (`ClientFluids`). `FluidSprites` delegates its tint to it on every node, and its still texture on 1.21.x only (`<26.1`). On `>=26.1` the still sprite reads the shared static `ClientFluids.model(BCFluidStack)` (the one missing-texture-to-water fallback, which `NeoForgeClientFluids` and `FabricClientFluids` use too), so the sink's `stillTexture` is read by the pre-26.1 `FluidSprites` alone; `FabricClientFluids.stillTexture` carries the water fallback as well, so it is no longer a latent gap. Making `FluidSprites` read the sink on every node would change the client fluid render path on 26.x and is deferred (follow-up).

## Hidden tooling costs

These are NeoForge-only today and need Fabric twins or loader-awareness:
- **Tests:** FML-JUnit (`neoForge { unitTest }`). The game tests run on Fabric since Phase 2c.
- **Guard testers:**
  - `StonecutterDirectiveGuardTester`: loader terms, suffixed active node.
  - `MainSourceSet` and the `buildcraft.test.mainSourceDirs` property: every source set must be passed.

  - `CopyrightHeaderTester`: new files.
  - `FabricChunkTicketsGuardTester`: a source pin where no run can stage the event (a level unload), see Fabric bugs below.

## Open questions for the user

1. **Config on Fabric:** Forge Config API Port, which keeps `ModConfigSpec` in common code allowlisted but is unverified for `LOCAL` on 26.3, or an in-house builder over `ModConfigSpec` (about 9 files, which ends the exemption)? Recommendation: decide after the spike checks FCAP `LOCAL` support. Phase 1 S6 only seams registration, either way. **Taken (2026-11-04, orchestrator, reversible): Forge Config API Port.** FCAP 26.3.1 for Fabric ships `ModConfigSpec`/`ModConfig` and `ConfigRegistry`/`ModConfigEvents`; it has no `LOCAL` type (its set is COMMON, CLIENT, SERVER, STARTUP), so `FabricConfigRegistrar` maps LOCAL and COMMON to its COMMON (both sides, one file, never synced). The only loss is that a NeoForge 26.3 SYNCED spec is not synced on Fabric. `ModConfigSpec` stays allowlisted in common code.
2. **Fabric spike timing:** may a compile-only, non-shipping `26.3-fabric` node land right after S1, so build-level and seam-shape risks surface before the expensive slices? Recommendation: yes. **Taken (landed with the spike, #100):** the compile-only node landed right after S1 and grew into the shipping node.
3. **BC's own events** (`api/events/*`, `EventBuildCraftReload`, `RobotEvent`): move them to BC-owned listener lists, in the style of `PipeEventBus`, so third-party mods stop seeing them on the NeoForge bus? Or keep posting them on the NeoForge bus through the platform? Recommendation: BC-owned, since no addon consumes them. **Taken (2026-11 parity decision, owner): both.** BC-owned lists are the API, and on NeoForge the events are also posted on the NeoForge bus after them, so NeoForge behaviour matches `main` (see Events and lifecycle, BC's own events).
4. **Accept the Fabric fluid granularity gap?** BC stays integer mB; on Fabric, transfers below 81 droplets are rejected. **Taken (accepted):** foreign fluid moves on Fabric are whole millibuckets or nothing (see Transfer, Fabric transfer).
5. **Accept that worlds do not move between loaders?** Attachments and some NBT roots differ. **Taken (accepted):** cross-loader world portability is out of scope (see Attachments).
